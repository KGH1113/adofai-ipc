# AdofaiIpc 0.4.3

Fixes the standalone IPC transition that could report a successful 0.4.2 update
while still executing 0.4.1 code in Unity Mono. Existing 0.4.1 and 0.4.2
installations receive this correction through the same automatic update URL.

Mono can unify weak-named assemblies by simple name even after `LoadFrom` is
given a new versioned path. The launcher and runtime now have a stable distinct
public-signed identity, preserving the filenames and simple names accepted by
the published package validators. The launcher checks the actual loaded image
and updates `Info.json` atomically only after runtime initialization succeeds.
The public key is used for assembly identity; SHA-256 checks protect package
integrity. No private signing credential is included or required to build.

The legacy server also continues to the next configured port when Unity Mono
reports an occupied port as `SocketException` during the SDK transition.

After the old launcher/shim finishes committing its state, the running runtime
removes the standalone IPC folder once the installed Helper/Replay consumers
have migrated. There is no modal, restart prompt or forced restart. As in the
original transition, failed or incomplete consumer migrations retain IPC.

Validation includes the normal build/package suites, unmodified published
0.4.1 and 0.4.2 installers and shims in a single Unity Mono AppDomain, real new
code execution and metadata promotion, and isolated Unity Play Mode runtime
startup/frame-driven removal. This does not claim a complete ADOFAI gameplay
or Windows file-lock E2E pass. Locked detached files can remain outside Mods.

Keep 0.4.3 as GitHub Latest. SDK-only releases must preserve the standalone
update channel (publish them with `--latest=false`). Helper and Replay remain
at 1.0.0; no reinstall is required for an existing 0.4.2 test installation.
